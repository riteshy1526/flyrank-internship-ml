FlyRank ML Internship Capstone

Content Refresh Opportunity Scoring for Search Discovery

Lane: Refresh / Content Opportunity Scoring Model: Random Forest vs transparent baseline

Abstract

Maintaining high-quality content is essential for sustained search visibility and user engagement. Using the anonymized FlyRank internship dataset, this project studies which content pages should be prioritized for refresh based on historical search performance, engagement, freshness, and content characteristics. A transparent rule-based baseline and a client-aware machine learning model were compared on the same validation split. In this sample, the learned model materially improved the quality of the top-ranked review queue: Precision@50 rose from 0.24 to 0.74, roughly a 3× lift in the most actionable review candidates. The final output is a ranked reviewer queue with interpretable reasons, designed to support editorial decision-making rather than replace it.

1. Introduction / Problem statement

The core decision this work supports is simple: given a limited editorial budget, which pages should a reviewer inspect first? Search teams cannot manually review every content page, and the cost of a wrong decision is wasted effort. The aim is to identify pages that are visible, stale, declining, or underperforming in their current state and therefore most likely to benefit from a refresh.

This is a prioritization task, not a claim that we can predict the Google algorithm. The output is a ranked review queue built from measured signals in anonymized historical search data, intended as decision support for human editors and content strategists.

2. Data

The analysis uses the anonymized starter dataset shipped with the FlyRank ML Internship repository: data/raw/content_refresh_anonymized.csv. It contains roughly 30,000 content rows with search demand, engagement, content age, freshness, and position signals, aggregated at a per-content level. The target used in the modeling step is is_declining_label, a public-safe label based on the observed trend direction.

Public-safety rules were followed throughout: no client names, no domains, no URLs, no private queries, and no sensitive business data were used. The repo’s data guidance also highlights important caveats: rate columns are x100 percentages, avg_position = 0 means no data rather than a rank of zero, and label-derived trend fields are never used as model features.

  • Rows used: ~30,000
  • Target positive rate: about 54.2%
  • Split strategy: client-aware holdout
  • Excluded: fields that would leak the target or reveal private client context

3. Methodology

The task was framed as a binary classification problem: identify content pages likely to be in a declining refresh state based on historical search and engagement patterns. The validation design used a client-aware holdout split rather than a random row split so that patterns from the same client would not leak between training and evaluation.

Features included search volume, impressions, clicks, CTR, average position, engagement rate, scroll rate, content age, freshness, and content-type-related metadata. The transparent baseline was a hand-written rule combining visibility, freshness risk, depth gap, and page-position opportunity. The learned models compared logistic regression, decision tree, and random forest models, with model selection based on Precision@50 because the highest-value part of the queue is the top-ranked subset a human reviewer can act on.

Leakage checks were explicit: label-derived trend fields were not used as features, the target was defined from the observed downward trend, and the holdout was grouped by client identity to reduce leakage risk.

5. Limitations and honest framing

This work is a decision-support model based on a single anonymized sample. It should not be interpreted as a universal law of search, nor as a causal test of content-refresh interventions. It measures patterns in observed data and translates them into a reviewer queue.

The model is strongest for prioritization and weakest for causal inference. A page flagged by the model is not automatically a page that must be edited; editorial context, content strategy, product goals, and business priorities still matter. The client-aware holdout reduces leakage risk, but it does not eliminate all drift risk across content types or traffic regimes.

The safe interpretation is directional and operational: this is a way to narrow the queue, not a command to publish or change content without review.

6. Ranked recommendations

  1. Start with the top-ranked refresh queue. Focus attention on pages with visible demand, declining trend direction, and low CTR or weak engagement.
  2. Use the model to triage, not to automate. Treat the queue as a reviewer shortlist and confirm with editorial judgement.
  3. Prioritize pages with measurable opportunity. Pages with strong impressions and weak engagement are usually the best candidates for an update.
  4. Monitor rather than fix. Some pages are visible but not yet risky enough to justify immediate investment; they belong in a monitoring lane.
  5. Watch content-age and freshness signals. Older pages with sustained traffic and weak engagement are often more valuable candidates than low-volume pages.

7. Reproducibility

The project is reproducible from the repository and the bundled sample data. The reference pipeline includes the feature preparation, transparent baseline, model training, evaluation, and final queue export.

To reproduce the workflow from a fresh clone:

python scripts/run_all.py

This regenerates the prepared feature vector, baseline queue, trained models, evaluation metrics, charts, and final report.
